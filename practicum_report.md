# Отчет по практикуму

Дата выполнения: 2026-09-14

Практикум выполнен в двух отдельных репозиториях: `clean_order_service` и `git-master-lab`.

## Часть 1. Clean Architecture

В репозитории `clean_order_service` создано небольшое Python-приложение для оформления заказа. Код разделен на слои:

- `domain` - доменные сущности `Order` и `OrderItem`, а также правило скидки;
- `use_cases` - сценарий `CreateOrderUseCase` и интерфейс репозитория;
- `infrastructure` - in-memory реализация хранилища;
- `main.py` - точка сборки приложения.

Бизнес-правило: если сумма заказа от 5000 рублей, применяется скидка 10 процентов. В демонстрационном запуске сумма без скидки равна 9100.0 руб., итоговая сумма равна 8190.0 руб., статус заказа - `CREATED`.

В Git-истории первой части есть отдельные ветки `feature/domain-entities` и `feature/use-cases`, а их интеграция выполнена через `merge --no-ff`, чтобы сохранить видимую историю разработки.

### Ответы на контрольные вопросы

1. В доменном слое нельзя импортировать SQLAlchemy, sqlite3, Django ORM и похожие библиотеки, потому что доменная модель должна описывать бизнес-правила, а не способ хранения данных. Если привязать ее к конкретной базе, приложение будет сложнее тестировать и переносить.
2. `interfaces.py` задает контракт репозитория. Use case зависит от абстракции `IOrderRepository`, а не от конкретного класса, поэтому инфраструктуру можно заменить без изменения бизнес-логики.
3. `--no-ff` нужен, чтобы после слияния остался отдельный merge-коммит. По истории видно, какие изменения пришли из конкретной ветки и какой блок работы они закрывали.

## Часть 2. Git Master Lab

В репозитории `git-master-lab` отработаны основные и продвинутые операции Git:

- настройка `.gitignore` с исключением `important.log`;
- индексация, `diff`, коммиты, `git mv`, `git rm`;
- ветка `feature/payment`, merge-коммит и аннотированный тег `v1.0.0`;
- `stash` для временной незавершенной правки;
- ветка `hotfix/license-header` и выборочный перенос коммита через `cherry-pick`;
- `revert`, `clean`, ручное разрешение конфликта в `service.cfg`;
- rebase ветки `feature/rebase-test`;
- восстановление после `reset --hard` через `reflog`;
- `blame` для `config.js`;
- `bisect` для поиска коммита, где появилась строка `CRITICAL_BUG = TRUE`.

Конфликт в `service.cfg` был решен в пользу защищенного адреса API:

```text
API_URL=https://api.v2-secure.example.com
API_VERSION=2.0
```

`git bisect` нашел регрессию в коммите `chore: routine update 1`, где впервые появилась строка `CRITICAL_BUG = TRUE`.

## Итог

Оба репозитория находятся в рабочем состоянии. Первая часть показывает разбиение приложения по слоям Clean Architecture, вторая часть демонстрирует практическое владение командами Git из задания.
